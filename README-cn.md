# 里程碑复盘：整理你的代码库文档

> 项目稳定了，趁着记忆还新鲜，把学到的东西写下来。

## 概述

经过前面的课程，你已经构建了一个完整的 AI 作品集网站：Landing Page、AI Chatbot、Vercel 部署。功能都跑通了。

现在是一个好时机——**停下来，复盘一下，把知识沉淀成文档**。

为什么要现在做？回想一下 30% 法则：项目到了 30% 的时候，你既能看清全貌，又还有精力整理。再往后走，细节会越来越模糊，等你三个月后回来改代码，可能连自己当时怎么搭的都忘了。

这节课的目标很简单：**读懂导师写的文档，然后自己也写一篇**。

## 学习目标

这节课你会学到：

1. **理解两类文档的作用** — decisions（决策记录）和 dev-guide（开发指南）各有什么用
2. **复习代码库结构** — 通过读文档快速回顾项目架构
3. **练习写技术文档** — 自己动手写一篇，锻炼"把知识写下来"的能力

## 核心概念

### 两类文档

导师已经帮你整理好了两类文档，它们的用途不同：

| 类型 | 位置 | 用途 |
|------|------|------|
| **Decisions** | `docs/decisions/` | 记录"当时为什么这么做"的决策理由 |
| **Dev Guide** | `docs/dev-guide/` | 记录"这个代码库怎么跑起来"的开发指南 |

**Decisions（决策记录）** 回答的是 "Why"：
- 为什么用 pnpm 而不是 npm？
- 为什么要生成 requirements.txt？
- Vercel 的计费模式是怎么回事？

**Dev Guide（开发指南）** 回答的是 "How"：
- 代码库的目录结构是什么？
- 前端/后端各有哪些关键文件？
- 想改某个功能应该去哪里改？

### 为什么要写文档？

这些文档很"功利"——都是为了以后有用：

- **三个月后你回来改代码**，忘了当时怎么配的 → 读 Dev Guide
- **想知道为什么要这么做**，而不是那么做 → 读 Decisions
- **新队友加入项目**，需要快速上手 → 直接丢文档链接

写文档不是浪费时间，是**给未来的自己和队友省时间**。

## 练习

### 练习 1：阅读 Dev Guide

**目标：** 通过阅读文档快速复习代码库结构。

**你要做的：**

1. 打开并阅读这四篇开发指南：
   - [01-overview-CN.md](./docs/dev-guide/01-overview-CN.md) — 项目架构总览
   - [02-backend-walkthrough-CN.md](./docs/dev-guide/02-backend-walkthrough-CN.md) — 后端代码详解
   - [03-frontend-walkthrough-CN.md](./docs/dev-guide/03-frontend-walkthrough-CN.md) — 前端代码详解
   - [04-faq-CN.md](./docs/dev-guide/04-faq-CN.md) — 常见问题与操作手册

2. 边读边问自己：
   - 这些内容我之前学过吗？
   - 有没有哪些细节我已经忘了？
   - 如果三个月后我回来，这篇文档够用吗？

**为什么这么做：**

读别人写的文档，是学习"怎么写好文档"的第一步。注意文档的结构：先概览，再细节，最后是速查表。

---

### 练习 2：阅读 Decisions

**目标：** 理解项目中的关键决策及其背后的原因。

**你要做的：**

1. 打开并阅读这四篇决策记录：
   - [vercel-active-cpu-billing-CN.md](./docs/decisions/vercel-active-cpu-billing-CN.md) — Vercel 计费模式
   - [vercel-framework-detection-CN.md](./docs/decisions/vercel-framework-detection-CN.md) — Framework 检测问题
   - [vercel-pnpm-package-manager-CN.md](./docs/decisions/vercel-pnpm-package-manager-CN.md) — 为什么用 pnpm
   - [vercel-python-uv-requirements-CN.md](./docs/decisions/vercel-python-uv-requirements-CN.md) — Python 依赖管理

2. 注意每篇的结构：
   - **背景** — 遇到了什么问题？
   - **为什么** — 为什么要这样解决？
   - **怎么做** — 具体操作步骤

**为什么这么做：**

Decision 文档不是教程，而是"考古记录"。它帮你理解：**当时做这个决定的上下文是什么**。这在你需要改变决策时特别有用——你知道当初为什么这么选，才能判断现在是否需要改。

---

### 练习 3：自己写一篇文档

**目标：** 动手写一篇技术文档，练习"把知识写下来"的能力。

**你要做的：**

1. 选一个你在这个项目中学到的东西，比如：
   - 某个你踩过的坑（怎么发现的、怎么解决的）
   - 某个让你印象深刻的概念
   - 某个你想记录下来供以后参考的操作

2. 在 `docs/` 目录下新建一个 markdown 文件，写下来

3. 可以借助 AI 帮你写：
   ```
   帮我写一篇关于 [xxx] 的技术文档，记录 [背景、问题、解决方案]
   ```

4. 写完后分享给导师，作为这节课的小作业

**文档建议结构：**

```markdown
# 标题

## 背景
遇到了什么问题？上下文是什么？

## 解决方案
怎么解决的？

## 关键点
有什么要注意的？

## 参考
相关链接或命令
```

## 总结

这节课做的事情很简单：**读文档、写文档**。

但这背后是一个重要的习惯：**项目到了 milestone，停下来整理**。

很多人觉得写文档浪费时间，赶着写下一个功能。结果三个月后回来，对着自己的代码一脸懵。

**好的工程师不只是写代码，还要写文档**。文档是给未来的自己、给队友的礼物。

---

## 导师笔记

**为什么安排这节课：**

学生往往觉得"功能做完了就完了"。但在真实工作中，代码只占一半，**文档、复盘、知识沉淀**占另一半。

我见过太多项目，代码写得很好，但没有文档。结果换个人接手，要花一周时间才能搞懂架构。这一周本来可以省下来的。

**这节课的真正目的：**

1. **让学生养成写文档的习惯** — 不是等到最后才写，而是边做边记
2. **让学生知道文档该写什么** — 不是事无巨细，而是"以后会用到的信息"
3. **让学生通过读文档来复习** — 读完之后对项目结构更清晰

**关于"自己写一篇"：**

这个作业故意很开放。学生可以写任何东西——踩过的坑、学到的概念、操作手册。

重点不是写得多好，而是**开始写**。

很多学生第一次写会觉得"没什么好写的"。但真正动笔之后，会发现"原来我学了这么多东西"。

**这就是复盘的力量。**
