# Same Idea, Different Skin

## A Familiar Feeling

今天的任务很简单：把 Node.js 和 pnpm 装上，为接下来的 Next.js 前端做准备。

以前搜教程，清一色都是教你装 nvm + npm 的。但经历了上次 mise + uv 那一轮之后，我甚至没有去搜教程，而是直接：

```bash
mise use -g node@lts
mise use -g pnpm@latest
```

两行。搞定。

然后我随手查了一下 pnpm 的文档，想了解一下它跟 npm 到底有什么区别。

结果越看越觉得眼熟。

---

## Déjà Vu

pnpm 的核心卖点是什么？**所有的包只在磁盘上存一份，项目里通过 hardlink 引用。**

等一下，这个思路我是不是在哪里见过？

uv——Python 的依赖管理，核心也是这个逻辑。不重复存储，通过 link 共享。

mise——runtime 版本管理，核心还是这个逻辑。Python 3.12 只装一次，所有需要它的项目共同引用。

三个工具，三个不同的语言生态，解决的是三个不同层面的问题。但掀开盖子一看，里面跑的是**同一个引擎**：

> **相同的东西只存一份，需要的时候引用过去。**

计算机科学里这甚至不是什么新概念——这不就是数据库里的"范式化"吗？不就是操作系统里"共享库"的思路吗？不就是所有人第一节数据结构课学到的"引用 vs 复制"吗？

原来真正伟大的设计思路就是这么朴素。朴素到跨越了语言、跨越了工具、跨越了时代，大家最终都会走到同一个答案上。

---

## The Payoff of Going Deep

不过让我最开心的不是这个发现本身，而是另一件事：

**我几乎没有花时间学 pnpm。**

因为我已经理解了 uv 的设计逻辑，当我看到 pnpm 的文档时，脑子里自动就把它们对应上了。content-addressable store？哦，就是 uv 那个全局缓存。hardlink？哦，就是 mise 那个 shims 目录的变体。lockfile？一样的，精确锁定版本。

上一篇里我说过，花时间去理解底层原理，这些知识不会因为工具更新换代而过时。

没想到这句话这么快就被验证了。才过了一篇博文而已。

当你搞懂了一个东西"为什么"这么设计，而不只是"怎么"用它，再遇到类似的东西时，学习成本几乎是零。因为你不是在学一个新工具，你只是在认一张熟面孔。
