听起来应该很简单对吧？把代码拼一拼就行了嘛。

然后我发现，事情没那么简单。

## The Translation Problem

问题出在"语言不通"。

前端用的是 Vercel AI SDK，它发出来的数据长这样：

```json
{
  "role": "user",
  "parts": [{"type": "text", "text": "你好"}]
}
```

后端要调用的是 AWS Bedrock，它期望的格式是这样：

```json
{
  "role": "user",
  "content": [{"text": "你好"}]
}
```

看到了吗？一个用 `parts`，一个用 `content`。结构也不一样。

这就像两个人，一个说普通话，一个说粤语。虽然都是中文，但直接对话会出问题。你需要一个翻译。

不仅如此，Bedrock 返回的响应也是一堆嵌套的字典：

```python
response["output"]["message"]["content"][0]["text"]
```

每次都要这样一层层剥洋葱，又丑又容易写错。

这时候我意识到：**我需要工具。**

---

## Standing on Shoulders

好消息是，我不用从零开始造轮子。

开源社区已经有人解决了这些问题。`vercel-ai-sdk-mate` 可以把前端的数据格式转成 Python 对象，`boto3-dataclass` 可以把 Bedrock 的响应转成带类型的 dataclass。

但我没有满足于"能用就行"。

我去读了这些库的源码。不是因为我喜欢折腾，而是因为我想知道：**它们到底做了什么？**

结果发现，核心逻辑简单得让人意外。

---

## The Simplicity of Dataclass

`boto3-dataclass` 做的事情，说白了就是一句话：**把字典的键值对，变成对象的属性。**

原本你要这样写：

```python
text = response["output"]["message"]["content"][0]["text"]
```

现在可以这样写：

```python
text = response.output.message.content[0].text
```

就这？就这。

但这个"就这"背后，藏着一个重要的设计理念：**把数据结构的细节封装起来，让使用者只关心"我要什么"，而不是"它存在哪"。**

IDE 可以自动补全了。类型检查可以帮你找错了。代码读起来像自然语言了。

这不是什么高深的技术。这是工程师的品味。

---

## The Real Skill

说实话，这两个工具不是我写的。是开源社区的大佬们造好了，我拿来用的。

但我觉得这不丢人。

因为我在用它们的过程中，搞懂了它们是怎么工作的。我知道 `vercel-ai-sdk-mate` 是怎么解析 JSON 的，我知道 `boto3-dataclass` 是怎么把字典映射成属性的。

更重要的是，我有信心：**如果下次遇到类似的问题，而且没有现成的轮子，我能自己造一个。**

这才是这节课真正教会我的东西。

工具本身不重要。Axios 也好，Fetch 也好，boto3 也好，它们都会过时，都会被更好的东西取代。

但"在需要的时候，能造出自己需要的工具"——这个能力不会过时。

## Reflection

回头看这个项目，从第一课到现在，我其实一直在做两件事：

第一，**学会用别人的工具**。Next.js、FastAPI、Bedrock API、Vercel AI SDK……这些都是别人造好的轮子，我学会了怎么开这辆车。

第二，**理解工具的底层**。不是停留在"会用"，而是去看它们是怎么设计的，解决了什么问题，做了哪些取舍。

第一件事让我能完成任务。第二件事让我能解决新问题。

大部分人只做第一件事。但真正能独当一面的工程师，两件事都做。

Dive deep，不是为了炫技，而是为了在没有现成答案的时候，能自己找到出路。
